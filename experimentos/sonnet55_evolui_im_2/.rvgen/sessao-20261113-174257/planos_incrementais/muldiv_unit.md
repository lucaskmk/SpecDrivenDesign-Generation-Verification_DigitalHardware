## Publica — incremento 1

Behavior: With funct3 = 0x0 (MUL) and the same operands as the smoke test, result is the low 32 bits of the product, not the high word MULHU returned.
Coverage gap: Section 1, multiplier-group operation selection by funct3(1 downto 0). The only witness is funct3=0x3 (MULHU). No test shows that changing funct3 alone moves result to a different multiplier operation, such as the low word instead of the high word.
Prerequisites: The smoke test passes. It shows that the combinational multiplier path settles and drives result for MULHU on operand_a = 0x80000000 and operand_b = 0xFFFFFFFF, with no clock or reset needed.
New factor: funct3 selects MUL (low product word) instead of MULHU (high product word) on identical operands.
Stimulus: Reuse the smoke operands (operand_a = 0x80000000, operand_b = 0xFFFFFFFF) and change only funct3 to the MUL encoding. Wait for the combinational result to settle. Compare all 32 bits with the independent Python reference, which gives 0x80000000. The MULHU value 0x7FFFFFFF differs from it, so a stuck or mis-sliced selection is detected.
Support/witness path: None needed. result is directly observable on the public port. The existing MULHU smoke result is the baseline that this case contrasts with.
Public observations: The full 32-bit result after settling, compared with the reference value for MUL on these operands. Optionally, assert that it differs from the MULHU value 0x7FFFFFFF already witnessed.
Forbidden: Do not drive the divider group (funct3 with bit 2 set) in this case. Do not change the operands, add operand-swap or signedness variations, run walks or random sweeps, or use the sweep of all 8 funct3 values. Do not touch internal signals such as dut.u_mul, dut.mul_op, dut.mul_result or dut.div_result. Do not drive U/X/Z values. Do not use a clock or reset.

## Publica — incremento 2

Behavior: MULHSU (funct3 = 0x2) returns the high 32 bits of the product with operand_a read as signed and operand_b read as unsigned. On operand_a = 0x80000000 and operand_b = 0xFFFFFFFF the exact product is -2^31 x (2^32 - 1), and the high word is 0x80000000.
Coverage gap: Multiplier ops 01 (MULH) and 10 (MULHSU) have no public-port witness. Only MUL (000) and MULHU (011) are covered, so signed interpretation of operands in the high-word product is untested. MULHSU is the least complex gap because it stays in the multiplier group, which is already witnessed.
Prerequisites: The smoke test shows MULHU returns the high word, 0x7FFFFFFF, on these operands. The approved case shows funct3 alone changes the multiplier result, and that MUL gives 0x80000000 on the same operands. The multiplier group is reachable and reads operand_a and operand_b without a swap.
New factor: Signed interpretation of operand_a combined with unsigned interpretation of operand_b in the multiplier high word (MULHSU)
Stimulus: Reuse the operand pair from the existing suite, where both operands have bit 31 set. Select MULHSU by changing only funct3 from an already witnessed multiplier operation. The reference model computes the expected value as signed operand_a times unsigned operand_b, reduced modulo 2^64, taking the high word.
Support/witness path: Support only: the MULHU baseline (funct3 = 0x3) on the same operands, already shown to give 0x7FFFFFFF. Compare against it, but do not count it as new coverage and do not re-assert it as a new claim.
Public observations: After the inputs settle, all 32 bits of result must equal the reference value 0x80000000. The result must differ from the MULHU result 0x7FFFFFFF on identical operands. This separates MULHSU from MULHU, which reads operand_a as unsigned. Optionally record that it also differs from the MULH value 0x00000000 on the same operands, which shows operand_b is read as unsigned. Use only dut.operand_a, dut.operand_b, dut.funct3 and dut.result.
Forbidden: Do not drive or read internal signals (mul_op, div_signed, div_rem, u_mul, u_div and so on). Do not use divider funct3 values 0x4 to 0x7. Do not add a sweep over all 8 funct3 values, operand-swap checks, bit-position walks or random regression. Do not use an operand pair that only repeats the MUL versus MULHU relation with different literals. Do not use X, Z or U on inputs. Do not use a clock or reset. Do not assert closed-form single-bit expectations for MULH or MULHSU when operand bit 31 is set. Take expected values from the independent Python reference only.

## Publica — incremento 3

Behavior: With fixed operands, funct3 = 001 makes result the high 32 bits of the product with both operands read as two's-complement signed values. The signed reading of operand_b is what separates it from MULHSU and MULHU.
Coverage gap: Selection of MULH (funct3 = 001, signed x signed high word) in the multiplier group. The suite has public-port witnesses only for MUL (000), MULHSU (010) and MULHU (011). The signed-by-signed interpretation of operand_b has no witness, and neither does the funct3 decode that selects it. No divider operation (100..111) has a witness either, but that is a more complex behavior and comes after this case.
Prerequisites: Smoke test: MULHU on the most-negative value times all-ones passes; lote-001: MUL on the same operands passes, so funct3 changes alone move the result; lote-002: MULHSU on the same operands passes, so the signed-a / unsigned-b high word is already witnessed
New factor: funct3 selects MULH (signed x signed high word)
Stimulus: Keep the operands used by the existing multiplier cases: operand_a is the most-negative 32-bit value and operand_b is all-ones. Support: apply the already-witnessed MULHSU selection and use it only as a reference value that MULH must differ from. Then change only funct3 to the MULH encoding. Compare the full 32-bit result with an independent reference that reads both operands as signed (here -2^31 x -1 = +2^31, whose high word is zero). The expected value differs from the MULHSU, MULHU and MUL results already observed on these operands.
Support/witness path: Drive the operands, apply MULHSU as support and capture its result, then change only funct3 to MULH. The only public observation is the result port, sampled after settling.
Public observations: result after funct3 selects MULH equals the full 32-bit reference value for signed x signed high word; result differs from the MULHSU result captured as support on the same operands; result differs from the MULHU and MUL results already witnessed on the same operands
Forbidden: Do not read dut.mul_op, dut.div_signed, dut.div_rem, dut.mul_result, dut.div_result, dut.u_mul or dut.u_div, or any other internal signal; Do not use a divider funct3 value or add a divider case; Do not enumerate operand pairs or sweep all funct3 values; Do not change operands relative to the existing multiplier cases; Do not count the MULHSU support step as newly covered; Do not drive X, Z or U values; Do not use a clock or reset; Do not repeat the MUL, MULHSU or MULHU relations with different literals

## Publica — incremento 4

Behavior: With operands held fixed, setting funct3(2) to 1 makes result the divider's quotient instead of the multiplier's product. Use small positive operands, pair P2 (100, 7), with the signed-quotient selection (funct3 = 100, DIV). The signed and unsigned interpretations coincide on these operands, so the case does not test them.
Coverage gap: Strategy section 1 (operation selection by funct3), unit choice: funct3(2)=1 routing result to the divider. The suite has only multiplier-group witnesses (MUL, MULH, MULHSU, MULHU on 0x80000000 x 0xFFFFFFFF). No case selects any divider operation, so there is no public-port evidence that the divider output ever reaches result.
Prerequisites: Multiplier-group selection is already witnessed: the smoke test and lote-001..003 show funct3 changes alone alter result and that MUL, MULH, MULHSU and MULHU each give reference values. Combinational settling after changing only funct3 is also already exercised.
New factor: funct3(2) selecting the divider output (DIV quotient) instead of the multiplier output
Stimulus: Scenario class: ordinary, non-special operands (dividend 100, divisor 7, both positive, non-zero divisor, no overflow), so signedness, remainder selection and divide-by-zero are not involved. Support sequence: drive the operands with the multiplier low-word selection (MUL) and read the product as the baseline. This is support only and is not counted as newly covered. Focal step: change only funct3 to the signed-divide selection (DIV) with the operands unchanged, then read result again. The baseline product and the quotient differ on this pair, so a wrong or crossed-over unit selection is visible.
Support/witness path: Support: MUL on (100, 7) gives the reference product 0x000002BC, read through result after settling. Witness: DIV on the same operands gives the reference quotient 0x0000000E on result. Both are observed on the public result port only.
Public observations: On result, after settling and with operand_a and operand_b unchanged: (1) MUL baseline equals the reference product 0x000002BC; (2) after changing only funct3 to DIV, result equals the reference truncated quotient 0x0000000E, compared on all 32 bits; (3) the DIV result differs from the MUL baseline value 0x000002BC. Expected values come from the independent Python reference.
Forbidden: Do not use dut.mul_op, dut.div_signed, dut.div_rem, dut.mul_result, dut.div_result or dut.u_mul/dut.u_div internals. Do not add divide-by-zero, signed overflow, negative operands, remainder or unsigned-divide checks. Do not sweep all 8 funct3 values or add further operand pairs. Do not drive clock or reset (none exist). Do not drive X, Z or U values. Do not reuse the 0x80000000 x 0xFFFFFFFF operands, where MUL and DIV coincide.
