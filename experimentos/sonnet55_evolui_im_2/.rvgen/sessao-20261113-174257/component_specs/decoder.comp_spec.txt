# Component semantic contract: decoder

## Public interface
```vhdl
entity decoder is
    port(
        instr : in std_logic_vector(31 downto 0);
        reg_write : out std_logic;
        mem_write : out std_logic;
        alu_src_a_pc : out std_logic;
        alu_src_b_imm : out std_logic;
        alu_control : out std_logic_vector(3 downto 0);
        branch_enable : out std_logic;
        jump : out std_logic;
        jalr : out std_logic;
        wb_select : out std_logic_vector(1 downto 0);
        muldiv_op : out std_logic
    );
end decoder;
```

## Responsibility
Decode RV32IM instruction opcode and function fields into register-write, memory-write, operand-source, ALU-operation, branch, jump, writeback-selection and M-extension-select controls.

## Timing

`decoder` is purely combinational. After `instr` changes, every output, including `muldiv_op`, settles to the value specified below without a clock edge. The decoder has no state, handshake or latency.

## Reset

None. The decoder has no reset input. All outputs, including `muldiv_op`, are determined solely by `instr`.

## Behavior

`instr` is a 32-bit RV32IM instruction. The decoder uses `instr[6:0]` as the opcode, `instr[14:12]` as `funct3`, and, where specified, `instr[31:25]` as `funct7`.

Two named output tuples are used throughout this contract:

- **UNSUPPORTED tuple:** `reg_write='0'`, `mem_write='0'`, `alu_src_a_pc='0'`, `alu_src_b_imm='0'`, `alu_control="0000"`, `branch_enable='0'`, `jump='0'`, `jalr='0'`, `wb_select="00"`, `muldiv_op='0'`.
- **M tuple:** `reg_write='1'`, `mem_write='0'`, `alu_src_a_pc='0'`, `alu_src_b_imm='0'`, `alu_control="0000"`, `branch_enable='0'`, `jump='0'`, `jalr='0'`, `wb_select="00"`, `muldiv_op='1'`.

For every recognized instruction encoding, the outputs match the instruction-class table below. For any unsupported opcode or unsupported function encoding, the outputs are exactly the UNSUPPORTED tuple (no architectural side effects).

For valid instructions, `reg_write` indicates that the instruction produces a register result. It is asserted for register-writing classes even when `rd` is `x0`. Suppressing writes to `x0` is the register file's responsibility. `mem_write` is asserted only for valid stores. `branch_enable` is asserted only for valid conditional branches. `jump` is asserted for `JAL` and `JALR`. `jalr` is asserted only for `JALR`.

`muldiv_op` is `'1'` only for the eight valid RV32M instructions (opcode `0x33`, `funct7="0000001"`, any `funct3`). It is `'0'` for every other instruction, including all RV32I instructions and all unsupported encodings.

`alu_src_a_pc` selects the PC as ALU operand A when `'1'`, and `rs1` otherwise. `alu_src_b_imm` selects the instruction's applicable immediate as ALU operand B when `'1'`, and `rs2` otherwise.

Valid instruction classes and their controls:

| Instruction class | `reg_write` | `mem_write` | `alu_src_a_pc` | `alu_src_b_imm` | `branch_enable` | `jump` | `jalr` | `wb_select` | `muldiv_op` |
|---|---:|---:|---:|---:|---:|---:|---:|---|---:|
| OP, RV32I (`0x33`, valid `funct7`/`funct3` pairs from `Operations`) | 1 | 0 | 0 | 0 | 0 | 0 | 0 | `"00"` | 0 |
| OP, RV32M (`0x33`, `funct7="0000001"`, any `funct3`) | 1 | 0 | 0 | 0 | 0 | 0 | 0 | `"00"` | 1 |
| OP-IMM (`0x13`) | 1 | 0 | 0 | 1 | 0 | 0 | 0 | `"00"` | 0 |
| Loads (`0x03`) | 1 | 0 | 0 | 1 | 0 | 0 | 0 | `"01"` | 0 |
| Stores (`0x23`) | 0 | 1 | 0 | 1 | 0 | 0 | 0 | `"00"` | 0 |
| Conditional branches (`0x63`) | 0 | 0 | 0 | 0 | 1 | 0 | 0 | `"00"` | 0 |
| LUI (`0x37`) | 1 | 0 | 0 | 1 | 0 | 0 | 0 | `"00"` | 0 |
| AUIPC (`0x17`) | 1 | 0 | 1 | 1 | 0 | 0 | 0 | `"00"` | 0 |
| JAL (`0x6F`) | 1 | 0 | 1 | 1 | 0 | 1 | 0 | `"10"` | 0 |
| JALR (`0x67`, `funct3="000"`) | 1 | 0 | 0 | 1 | 0 | 1 | 1 | `"10"` | 0 |

For JAL and JALR, `alu_control` is `"0000"`. Jump-target generation is not selected by `alu_control`.

## Operations

`alu_control` is a four-bit selector. Its meaning for non-branch instructions is:

| `alu_control` | Operation |
|---|---|
| `"0000"` | ADD |
| `"0001"` | SUB |
| `"0010"` | SLL |
| `"0011"` | SLT (signed) |
| `"0100"` | SLTU (unsigned) |
| `"0101"` | XOR |
| `"0110"` | SRL |
| `"0111"` | SRA |
| `"1000"` | OR |
| `"1001"` | AND |
| `"1010"` | PASS_B: the result is operand B |
| `"1011"`–`"1111"` | Not selected for non-branch instructions |

When `branch_enable='1'`, `alu_control` instead selects the branch condition:

| `alu_control` | Branch condition |
|---|---|
| `"0000"` | BEQ |
| `"0001"` | BNE |
| `"0010"` | BLT (signed) |
| `"0011"` | BGE (signed) |
| `"0100"` | BLTU (unsigned) |
| `"0101"` | BGEU (unsigned) |

The branch-specific meanings apply only when `branch_enable='1'`.

`wb_select` is a two-bit selector:

| `wb_select` | Writeback source |
|---|---|
| `"00"` | ALU result (for `muldiv_op='1'` the value is still routed through the `"00"` selection; the CPU uses `muldiv_op` to substitute the M-unit result) |
| `"01"` | Data-memory read result |
| `"10"` | `PC + 4` |
| `"11"` | Reserved; never produced |

`muldiv_op` is a one-bit select. When `'1'`, the instruction is an RV32M operation. The specific operation is identified downstream by `instr[14:12]`: `"000"` MUL, `"001"` MULH, `"010"` MULHSU, `"011"` MULHU, `"100"` DIV, `"101"` DIVU, `"110"` REM, `"111"` REMU. The decoder does not encode the M operation in `alu_control`; for M instructions `alu_control` is `"0000"`. Division-by-zero and overflow are operand-dependent and belong to the downstream M unit, not the decoder.

Opcode and function decoding:

| Opcode | Required function encoding | `alu_control` | `muldiv_op` |
|---|---|---|---|
| `0x33` OP | `funct3="000"`, `funct7="0000000"` | `"0000"` ADD | 0 |
| `0x33` OP | `funct3="000"`, `funct7="0100000"` | `"0001"` SUB | 0 |
| `0x33` OP | `funct3="001"`, `funct7="0000000"` | `"0010"` SLL | 0 |
| `0x33` OP | `funct3="010"`, `funct7="0000000"` | `"0011"` SLT | 0 |
| `0x33` OP | `funct3="011"`, `funct7="0000000"` | `"0100"` SLTU | 0 |
| `0x33` OP | `funct3="100"`, `funct7="0000000"` | `"0101"` XOR | 0 |
| `0x33` OP | `funct3="101"`, `funct7="0000000"` | `"0110"` SRL | 0 |
| `0x33` OP | `funct3="101"`, `funct7="0100000"` | `"0111"` SRA | 0 |
| `0x33` OP | `funct3="110"`, `funct7="0000000"` | `"1000"` OR | 0 |
| `0x33` OP | `funct3="111"`, `funct7="0000000"` | `"1001"` AND | 0 |
| `0x33` OP | any `funct3`, `funct7="0000001"` | `"0000"` | 1 |
| `0x13` OP-IMM | `funct3="000"` | `"0000"` ADD | 0 |
| `0x13` OP-IMM | `funct3="001"`, `instr[31:25]="0000000"` | `"0010"` SLL | 0 |
| `0x13` OP-IMM | `funct3="010"` | `"0011"` SLT | 0 |
| `0x13` OP-IMM | `funct3="011"` | `"0100"` SLTU | 0 |
| `0x13` OP-IMM | `funct3="100"` | `"0101"` XOR | 0 |
| `0x13` OP-IMM | `funct3="101"`, `instr[31:25]="0000000"` | `"0110"` SRL | 0 |
| `0x13` OP-IMM | `funct3="101"`, `instr[31:25]="0100000"` | `"0111"` SRA | 0 |
| `0x13` OP-IMM | `funct3="110"` | `"1000"` OR | 0 |
| `0x13` OP-IMM | `funct3="111"` | `"1001"` AND | 0 |
| `0x03` Load | `funct3` in `"000"`, `"001"`, `"010"`, `"100"`, `"101"` | `"0000"` ADD | 0 |
| `0x23` Store | `funct3` in `"000"`, `"001"`, `"010"` | `"0000"` ADD | 0 |
| `0x63` Branch | `funct3="000"` | `"0000"` BEQ | 0 |
| `0x63` Branch | `funct3="001"` | `"0001"` BNE | 0 |
| `0x63` Branch | `funct3="100"` | `"0010"` BLT | 0 |
| `0x63` Branch | `funct3="101"` | `"0011"` BGE | 0 |
| `0x63` Branch | `funct3="110"` | `"0100"` BLTU | 0 |
| `0x63` Branch | `funct3="111"` | `"0101"` BGEU | 0 |
| `0x37` LUI | any `funct3` and `funct7` | `"1010"` PASS_B | 0 |
| `0x17` AUIPC | any `funct3` and `funct7` | `"0000"` ADD | 0 |
| `0x6F` JAL | any `funct3` and `funct7` | `"0000"` | 0 |
| `0x67` JALR | `funct3="000"` | `"0000"` ADD | 0 |

For OP (`0x33`), the complete set of valid `(funct7, funct3)` pairs is:

- `funct7="0000000"` with every `funct3` (ADD, SLL, SLT, SLTU, XOR, SRL, OR, AND).
- `funct7="0100000"` with `funct3="000"` (SUB) or `"101"` (SRA) only.
- `funct7="0000001"` with every `funct3` (the eight M operations).

Every other OP combination is unsupported and yields the UNSUPPORTED tuple. For OP-IMM, loads, stores, branches and JALR, function encodings not listed above are unsupported. LUI, AUIPC and JAL have no function-field restrictions.

## Edge cases

- OP RV32I encodings are valid only for the exact `funct7` values above. `funct7="0100000"` is valid only for `funct3="000"` (SUB) and `"101"` (SRA); for the other six `funct3` values it is unsupported.
- For OP with `funct7="0000001"`, all eight `funct3` values are valid and give the M tuple. This includes `funct3="000"` and `"101"`, whose RV32I forms also exist with other `funct7` values. The result does not depend on `rd`, `rs1`, `rs2` (including `rd=x0`) or `instr[24:7]` bits other than `funct3`.
- OP with `funct7="0000000"` is always a valid RV32I instruction for every `funct3`, with `reg_write='1'`, the matching ALU selector and `muldiv_op='0'`. It is never unsupported.
- The only unsupported OP `funct7` values that are one bit away from `"0000001"` are `"0000011"`, `"0000101"`, `"0001001"`, `"0010001"`, `"0100001"` and `"1000001"` (flipping bits 1 to 6 of `funct7`). Flipping bit 0 gives `"0000000"`, which is valid RV32I.
- `funct7="0000001"` with any opcode other than `0x33` never sets `muldiv_op`. In particular, OP-IMM (`0x13`) with `instr[31:25]="0000001"` follows the OP-IMM rules: valid for non-shift `funct3`, unsupported for `funct3="001"` and `"101"`. In every case `muldiv_op='0'`.
- `muldiv_op` is `'0'` for every unsupported instruction and for every non-OP opcode.
- `wb_select="11"` is reserved and never produced.
- SLLI, SRLI and SRAI are valid only for the exact `instr[31:25]` patterns shown. The shift amount is not decoded by this component.
- For non-shift OP-IMM instructions, `instr[31:25]` does not restrict validity or change the selected operation.
- `rd`, `rs1`, `rs2` and immediate bits do not change the controls except where explicitly used as function bits above.
- Any unsupported function combination, including an otherwise recognized opcode with an invalid `funct3` or required `funct7`, produces the UNSUPPORTED tuple.
- All outputs have defined binary values for every possible 32-bit `instr`; there are no don't-care outputs.

## Test strategy

Use a combinational Cocotb test that drives a complete 32-bit instruction, lets the outputs settle, and checks every output (including `muldiv_op`) against the contract. Run each case without clock or reset stimulus. Expected values must be derived from the `Behavior` and `Operations` tables, not from assumptions such as "any change away from M is unsupported". These tests observe the decoder's own ports directly. They do not claim that CPU public-port tests observe internal selectors.

1. **Opcode-class controls and writeback selection:** For each valid class in the `Behavior` table, drive a canonical instruction and check the complete output tuple. Use different `rd`, `rs1`, `rs2` and immediate values between cases so field changes cannot hide opcode-class errors. Include `rd=x0` for at least one RV32I register-writing instruction and one M instruction, and require `reg_write='1'`.

2. **OP operations (RV32I):** Exercise every valid RV32I OP `(funct7, funct3)` pair in `Operations`, holding opcode and other fields constant, and check the exact `alu_control`, `muldiv_op='0'` and the full tuple. For every `funct3`, also drive `funct7="0100000"`. It must be valid for `funct3="000"` (SUB, `"0001"`) and `"101"` (SRA, `"0111"`), and give the UNSUPPORTED tuple for the other six. For every `funct3`, also drive at least these unsupported `funct7` values: `"0000010"`, `"1000000"`, `"0100001"`, `"1111111"`. Each must give the UNSUPPORTED tuple (`muldiv_op='0'`).

3. **RV32M decoding and `funct7` neighbours:**
   - **M encodings:** For each of the eight `funct3` values with opcode `0x33` and `funct7="0000001"`, require the M tuple. Repeat with several `rd`, `rs1`, `rs2` values (including `rd=x0` and `rs1=rs2`) and with `instr[24:7]` (excluding `funct3`) set to random, all-ones and all-zeros patterns. The tuple must not change.
   - **Single-bit flips of `funct7`:** For each of the eight `funct3` values, flip exactly one bit of `funct7="0000001"` and require the following:

     | New `funct7` | Flipped bit | Expected tuple for every `funct3` |
     |---|---|---|
     | `"0000000"` | 0 | Valid RV32I OP: `reg_write=1`, `alu_src_a_pc=0`, `alu_src_b_imm=0`, `wb_select="00"`, `muldiv_op=0`, `alu_control` per funct3: `"000"`→`"0000"`, `"001"`→`"0010"`, `"010"`→`"0011"`, `"011"`→`"0100"`, `"100"`→`"0101"`, `"101"`→`"0110"`, `"110"`→`"1000"`, `"111"`→`"1001"`; all other controls 0 |
     | `"0000011"` | 1 | UNSUPPORTED tuple |
     | `"0000101"` | 2 | UNSUPPORTED tuple |
     | `"0001001"` | 3 | UNSUPPORTED tuple |
     | `"0010001"` | 4 | UNSUPPORTED tuple |
     | `"0100001"` | 5 | UNSUPPORTED tuple |
     | `"1000001"` | 6 | UNSUPPORTED tuple |

   - **Two-bit change to `"0100000"`:** For each `funct3`, drive `funct7="0100000"`. For `funct3="000"` expect SUB (`alu_control="0001"`) and for `"101"` expect SRA (`alu_control="0111"`), each with `reg_write=1` and `muldiv_op=0`. For the other six `funct3` values expect the UNSUPPORTED tuple.
   - **Single-bit flips of `funct3`:** With `funct7="0000001"`, every `funct3` value is valid, so changing `funct3` never leaves the M tuple. With `funct7="0000000"`, changing `funct3` selects the matching RV32I row. With `funct7="0100000"`, `funct3` flips between `"000"` and `"101"` are not one bit apart, so check each `funct3` value separately as above.
   - **Opcode changes:** Starting from an M-encoded instruction (`funct7="0000001"`), change only the opcode to each of `0x13`, `0x03`, `0x23`, `0x63`, `0x37`, `0x17`, `0x6F`, `0x67` and an unknown opcode. For each `funct3`, `muldiv_op` must be `'0'`, and the full tuple must equal what the contract gives for the resulting instruction. Examples: `0x13` with `funct3` `"001"`/`"101"` and `funct7="0000001"` is unsupported, while `0x13` with `funct3="000"` is a valid ADDI. `0x03` with `funct3` `"011"`, `"110"` or `"111"` is unsupported. `0x67` is valid only for `funct3="000"`.

4. **OP-IMM operations and function restrictions:** Exercise every valid OP-IMM row, changing only `funct3` or, for shifts, only `instr[31:25]` between related cases. Check the exact ALU selector, `muldiv_op='0'` and the full tuple. For SLLI, SRLI and SRAI, test permitted and disallowed upper-bit patterns. This explicitly includes `instr[31:25]="0000001"`, which is unsupported for `funct3="001"` and `"101"` and gives the UNSUPPORTED tuple. Also include `"0100000"` with `funct3="001"` (unsupported). For each non-shift `funct3`, vary `instr[31:25]` (including `"0000001"`) with other fields fixed and require unchanged controls and `muldiv_op='0'`.

5. **Loads and stores:** Exercise each valid load and store `funct3` independently, checking all outputs. Only loads assert `reg_write` and select `"01"`, only stores assert `mem_write`, and `muldiv_op='0'` in all cases. Vary `rd`, `rs1`, `rs2` and immediate fields (including `instr[31:25]="0000001"`) with opcode and `funct3` fixed, and require unchanged controls. Test every unsupported load/store `funct3` and require the UNSUPPORTED tuple.

6. **Branches:** Exercise all six valid branch `funct3` values, varying only `funct3`. Check `branch_enable`, the branch-specific `alu_control`, `muldiv_op='0'` and all other outputs. Test unsupported branch `funct3` values (`"010"`, `"011"`) and require the UNSUPPORTED tuple.

7. **Unrestricted instruction fields:** For LUI, AUIPC and JAL, vary `funct3` and `funct7` (including `"0000001"`) with opcode and other fields fixed. Require unchanged controls and `muldiv_op='0'`. Separately vary register-index and immediate bits and confirm the decoded controls do not change.

8. **JALR restriction and jump controls:** Check JAL and valid JALR as separate cases, requiring `jump='1'`, the specified `jalr` value, `wb_select="10"` and `muldiv_op='0'`. Vary JALR `funct3` across all values. The valid encoding must match the JALR row and every other value must give the UNSUPPORTED tuple. Include `funct7="0000001"` with JALR.

9. **Unknown opcodes and invalid encodings:** Drive representative unrecognized opcodes (including ones with `funct7="0000001"`) and every invalid function combination listed above. For each, check the entire UNSUPPORTED tuple, not only the side-effect flags.

10. **Reserved writeback and exhaustive sweep:** Sweep all opcodes × all `funct3` × representative `funct7` values (including `"0000000"`, `"0100000"`, `"0000001"` and the six unsupported single-bit neighbours). The sweep must compare against an independent reference model of the tables in this contract. It must require that `wb_select` is never `"11"`, that `muldiv_op='1'` if and only if opcode is `0x33` and `funct7="0000001"`, and that when `muldiv_op='1'` the other outputs equal the M tuple. No output may contain `'U'`, `'X'` or other non-binary values.

11. **Combinational response:** Apply consecutive instructions from different classes without any intervening clock, and after each change require the outputs to match that instruction's expected tuple. Include transitions between valid and unsupported instructions and between classes with different writeback and control selections. In particular, cover both directions of transitions among an M instruction, the RV32I OP instruction with the same `funct3` (`funct7="0000000"`), and an unsupported OP `funct7` (for example `"0000011"`), to detect stale `muldiv_op` or other stale outputs.
