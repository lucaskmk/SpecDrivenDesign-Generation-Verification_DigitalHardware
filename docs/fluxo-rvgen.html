Em uma frase: o que o professor descreveu já existe quase por inteiro no rvgen.
  • Contrato antes de código: cada bloco ganha um contrato em markdown, e um revisor confere se os contratos fazem sentido juntos.
  • Pilha: um bloco por vez; se não passar no teste, o próximo não começa. Quem escreve o teste não vê o VHDL.
  • Modelo: não é mais Ollama local. A chamada vai para o OpenRouter, modelo openai/gpt-5.6-luna (o que está no seu .env). Cada chamada é isolada, sem histórico.
  • Certificação: pelas specs, o rvverify é a única autoridade do veredito. Mas o código do rvgen hoje não chama o rvverify: julga com o spec-riscv-test (programas oficiais riscv-tests). Ver seção 6.

2 · Visão geral

Da specs/cpu.md até o veredito. O laço da direita no meio é a revisão de contratos; o da direita embaixo é a correção da CPU integrada.

3 · A pilha, componente por componente

É o coração do que o professor pediu. Com --gates-componentes, a ordem vem das dependências (folhas primeiro, cpu por último) e um bloco só começa quando o anterior está congelado.

Por que o testbench não vê o VHDL: se a mesma IA lesse o VHDL para escrever o teste, ela tenderia a testar o que o código faz, não o que o contrato exige. Aqui o testbench nasce só do contrato e das portas (_escrever_testbench: “the implementation is intentionally not provided”). O VHDL só aparece depois, na triagem de uma falha.

4 · Quando um teste falha: quem errou?

Falha de teste pode ser culpa do VHDL, do testbench ou do contrato. Antes de mexer em qualquer coisa, uma triagem classifica. Corrigir o lado errado seria desperdício de tokens e de iteração.

5 · CPU integrada, correção e veredito

Quando a pilha termina, o cpu já passou no próprio testbench de IA. Agora entra o juiz externo. Aqui nenhuma IA decide se passou; a IA só ajuda a achar e corrigir o erro. O juiz que o código roda neste laço é o spec-riscv-test; a certificação pelas specs é o rvverify (seção 6).

No código atual, o veredito final (Agente.gerar, fim) roda a suíte completa sem filtro de casos e confere, antes, que nenhum arquivo do validador mudou durante a geração (arquivos_protegidos + hash_de). Se mudou, o veredito é recusado: a IA não pode alterar o juiz.

7 · Modelo e provedor: OpenRouter, sem Ollama

Seu .env tem SPECHDL_LLM_MODEL=openai/gpt-5.6-luna e uma chave do OpenRouter preenchida (só conferi se existe; não li o valor). Esse é o modelo externo padrão do rvgen (config.MODELO_EXTERNO_PADRAO). Presumo que “luna 6” seja esse gpt-5.6-luna.

Cuidado: o provedor padrão do código ainda é ollama. Sem --provedor openrouter (ou RVGEN_PROVEDOR=openrouter no .env), o rvgen procura um servidor Ollama e para com erro. O comando preparar também é pensado para Ollama; com OpenRouter ele só informa se a chave existe.

O que isso muda na prática

  • Sem exemplos: a flag --exemplo DIR (que cola uma CPU de referência no prompt) não é usada. O modelo recebe só o contrato, os specs e a descrição opcional, nunca uma CPU pronta.
  • Custo e velocidade: cada chamada é paga e sequencial (--parallel-testes 1 por padrão). As três flags de componente aumentam muito o número de chamadas. Não há medida de tempo ou custo com luna neste repositório: os 17–18 min registrados são do Ollama local de 14B. Meça numa primeira rodada.
  • Onde conferir o gasto: .rvgen/sessao-*/resultado.json (chamadas e tokens) e python -m rvgen comparar.
  • Limpeza do contexto: não existe memória entre chamadas; o que o modelo “lembra” é só o que o agente reenviou.
  • Quem executa GHDL: a IA só escreve texto. O GHDL, o cocotb e o spec-riscv-test rodam na sua máquina (--executor local) ou no Docker (spechdl-toolchain). Neste PC não achei ghdl, compilador RISC-V nem clone do riscv-tests no PATH; o Docker seria o caminho. Não verifiquei se a imagem já foi construída.

10 · O que uma geração deixa no disco

Tudo fica em <pasta da CPU>/.rvgen/sessao-*/, auditável depois. A IA só escreve em <pasta>/src/*.vhd; qualquer outro destino é recusado (_destino).

CaminhoO que é

testes/, testes_aprovados/testbenches cocotb gerados e a última versão que passou

11 · Comandos e flags

# modelo no OpenRouter (usa OPENROUTER_API_KEY e SPECHDL_LLM_MODEL do .env)
python -m rvgen gerar cpu_luna --provedor openrouter \
    --testes-componentes --gates-componentes --regressoes-componentes
python -m rvgen retomar ...              # continua sessão parada (exige as flags acima)
python -m rvgen comparar                 # várias rodadas lado a lado: veredito, tokens, custo

Um nome simples (cpu_luna) grava em experimentos/cpu_luna/; um caminho (entregas/minha_cpu) grava lá. Para não repetir --provedor, ponha RVGEN_PROVEDOR=openrouter no .env. --modelo troca o modelo só naquela rodada.

Sem flags

Contrato + revisão por bloco, escreve todo o VHDL e vai direto à suíte oficial. Não é a pilha do professor.

--testes-componentes

Gera e roda um testbench cocotb por bloco, mas só depois de escrever tudo.

--gates-componentes

A pilha de verdade: contratos globais revisados primeiro; depois VHDL → teste → congela, bloco a bloco.

--regressoes-componentes

Falha corrigida vira teste permanente, rodado nas correções seguintes.

--iteracoes N

Orçamento de correções (12). Também limita as correções de componente.

--provedor / --modelo

Padrão do código: ollama. O seu caso: openrouter. Também há vllm e google; chaves no .env.

Certificação pelas specs, por fora do rvgen (exige um cpu.toml na pasta): python -m rvverify experimentos/cpu_luna --keep --workdir relatorio. Para reproduzir o fluxo descrito pelo professor, use as três flags de componente juntas. Verificação independente do resultado: spec-riscv-test --cpu experimentos/cpu_luna --riscv-tests riscv-tests --out out.

13 · A confirmar com o professor

① Mesma IA nos dois papéis

VHDL e testbench usam o mesmo modelo (gpt-5.6-luna); o que muda é o contexto (o teste não vê o VHDL). Isso reduz o viés, não o elimina. Se ele quer modelos diferentes (ex.: um para VHDL, outro para teste), hoje não há opção para isso; seria uma mudança no rvgen.

② “Outra IA testa a CPU de novo”

Há dois níveis: o testbench de IA do bloco cpu (último da pilha) e depois a suíte oficial, que não é IA: são programas fixos. Faz sentido ser assim (juiz imparcial), mas vale confirmar que é isso que ele quer.

③ “luna 6”

Presumi openai/gpt-5.6-luna, que é o que está no .env e no README. Se o professor falou de outro modelo, é só --modelo ou SPECHDL_LLM_MODEL.
