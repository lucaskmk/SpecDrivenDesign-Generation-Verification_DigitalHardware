Mapa e revisão do projeto

Tudo o que existe no repositório, como as peças se ligam e uma revisão crítica com erros e sugestões. Estado lido no commit 2756083 (main, 29/10/2026). Para o detalhe do fluxo do gerador, veja fluxo-rvgen.html.

Visão Mapa Dois contratos Saúde Achados Sugestões O que está bom Limites
Resumo da revisão: a ideia está bem montada (contexto isolado, rollback, veredito só de execução), mas o repositório está no meio de uma migração. Os problemas mais sérios vêm disso:
  • As specs dizem que o rvverify certifica; o código do rvgen certifica com o spec-riscv-test.
  • O prompt manda a IA manter um generic que o validador rejeita (reproduzido).
  • O juiz final só roda em Linux/WSL; o Docker não serve, ao contrário do que a documentação sugere.
  • As CPUs de referência e o modelo de entregas/ seguem o contrato antigo e não casam com o rvverify atual (por leitura).
  • Testes: 21 falhas nas partes que consegui rodar, quase todas por dependência de máquina; o CI está apontado para uma pasta que não existe.

1 · O que é o projeto

Uma bancada para gerar e certificar CPUs RISC-V (RV32I, depois RV32IM) em VHDL. Uma IA escreve a CPU a partir de specs/cpu.md; GHDL e cocotb simulam; programas RISC-V reais decidem se passou. Mede-se também área, frequência e potência no Quartus. Duas frentes convivem: gerar com IA (rvgen) e avaliar CPU de aluno (rvverify + entregas/).

2 · Mapa do repositório

Linhas contadas só em arquivos versionados (.py .vhd .md .toml etc.). O repositório tem 70 commits de 3 autores (LKenji 39, Gabriel Oliveira Galazzi 30, Corsi 1). O último commit de código, bd302b6 (Corsi, 07/10), foi a reestruturação: apagou legado/ (a trilha A, Streamlit), REPO_MAP.md, docs/ antigos, specs/decisions.md, specs/tasks.md e as sessões reais de experimentos/ia_mono/. O CLAUDE.md também não existe mais.

5 · Achados

Ordenados por gravidade. Cada um diz como foi comprovado.

A1 · O prompt manda manter um generic que o validador rejeita altaexecutado

Renderizei o prompt de sistema real (texto_do_contrato, ~13 KB). Para RV32I ele diz: “keep the generic RV32M_ENABLE declared”. Para RV32IM: “decode … when the generic RV32M_ENABLE is true” e “the test bench runs the same CPU twice”. Mas specs/cpu.md (no mesmo prompt) exige a entidade exata, sem generic, e o validate_top do spec-riscv-test rejeitou uma entidade cpu com generic (“a entidade pública deve ser exatamente cpu”) e aceitou a mesma sem ele. Além disso spec-riscv-test/cli.py não menciona generic nenhum, então a afirmação de rodar duas vezes é falsa.

Efeito: um modelo obediente gera uma CPU que o juiz recusa antes de simular, e gasta rodadas pagas para descobrir isso. Para RV32IM o prompt descreve um mecanismo que não existe.

Correção: remover as duas frases do prompt (a ISA já é fixa por cpu.md) ou fazer o validate_top aceitar generics com valor padrão. Decidir antes de passar para RV32IM.

A2 · O juiz final só roda em Linux/WSL; o Docker não resolve altalidoexecutado

--executor docker termina com “spec-riscv-test não está instalado na imagem Docker; use --executor local”. A imagem spechdl-toolchain só tem binutils RISC-V (sem gcc, sem riscv-tests, sem spec-riscv-test), e o caminho padrão do executável é .venv/bin/spec-riscv-test (Linux). O rvgen preparar neste PC já acusa: “FALTA executor local: sem ghdl; resolver: wsl”. Mesmo assim --executor docker e RVGEN_EXECUTOR=docker continuam listados como opção no CLI e no .env.example; só funcionam para testes de componente.

Efeito: no Windows puro, rvgen gerar não passa nem da escolha do executor (felizmente antes de gastar token). ExecutorDocker.rodar_componente também usa os.getuid(), que não existe no Windows. Corrijo algo que eu disse antes: o Docker não é o caminho para o veredito.

Correção: documentar WSL2 como único ambiente suportado (com a lista exata de instalação), ou criar uma imagem completa (gcc RISC-V + riscv-tests + spec-riscv-test) e liberar o executor Docker para o veredito.

A3 · O rvverify não julga mais as CPUs de referência nem o _modelo altalido

O único testbench usado por conformance é rvverify.tb_virtual (barramento de 9 portas). A CPU pipeline tem topo CPU(rst, clk) com generics de ROM e memórias internas; a monociclo é igual; entregas/_modelo/cpu.toml e entregas/README.md ainda ensinam memórias fornecidas e ROM_INIT_FILE. tb_generic.py só é usado por testes. Resultado esperado: um aluno que seguir o README é reprovado por contrato, não por defeito.

Correção: portar uma CPU de referência (a monociclo é a mais simples) para o contrato virtual e usá-la como gabarito que o juiz precisa aprovar; reescrever entregas/README.md e o _modelo; ou, se o modo antigo ainda importa, reativar o despacho por [program].mode no conformance.

A4 · Quem é a autoridade do veredito? Specs e código discordam altalido

constitution.md, plan.md e spec.md (passo 8): rvverify. rvgen/executor.py e agente.py: spec-riscv-test, e o rvgen nunca chama o rvverify. Pelo título do commit 8aceaea (30/09, “executor do rvverify…”) e pelas sessões apagadas, até então o juiz do rvgen era o rvverify; a troca para o spec-riscv-test veio no bd302b6 sem atualizar a constituição. renderizar_cpu_toml existe em contrato.py mas só os testes a chamam, então o rvgen não produz o cpu.toml que o rvverify exige.

Correção: decisão do professor (ver as opções A/B/C do fluxo-rvgen), depois alinhar a constituição e o código. Sugestão provisória: B (spec-riscv-test no laço, rvverify como certificação final).

A5 · Rastreabilidade quebrada altaexecutado

90 arquivos citam FR-RV-xx, 64 citam ADR-xxx e 26 apontam para specs/decisions.md ou specs/tasks.md. Nenhum desses existe mais: specs/*.md tem 0 ocorrências de FR-RV. rvverify --listar imprime FR-RV-04, FR-RV-22. E specs/vhdl.md (regra 8) obriga todo VHDL gerado a começar com -- REQ: citando IDs de requisitos que a spec não define. Dos 26 VHDL do repositório, 13 têm essa linha.

Correção: ou restaurar uma lista curta de requisitos em spec.md, ou remover a regra 8 do prompt (ela gasta tokens e induz a IA a inventar IDs) e limpar as referências mortas.

M1 · Possível leitura adiantada no tb_virtual médiasuspeita, não executada

O tb_riscv escreve instr_data, faz await ReadWrite() e só então lê data_addr, com um comentário explicando que sem isso “a resposta pertence à instrução anterior”. O tb_virtual escreve instr_data e lê data_addr imediatamente, sem esperar. Em cocotb a escrita só vale depois da fase ReadWrite, então o endereço lido pode ser o da instrução anterior, o que daria load/store errado em CPU correta. Também descarta stores fora de 0x00FC8100 + 512 B sem avisar.

Verificar e corrigir: rodar o rvverify numa CPU conhecida-boa já portada (ver A3). Se confirmar, copiar o padrão do tb_riscv.

M2 · Testes dependem da máquina e a suíte da raiz não roda médiaexecutado

  • quartus_testing: 16 falhas: leem implemetation_tests/opus_5_RISCVIM/… (nome com erro de digitação), pasta que não está no repositório.
  • rvgen: 5 falhas: 3 de test_ollama esperam um modelo 14B e um executor pronto (dependem de GPU e GHDL do host); 2 de test_riscv_asm falham por falta de binutils em vez de pular.
  • pytest na raiz aborta na coleta (cocotb_tools) porque testpaths inclui cpus; quartus_testing/tests e spec-riscv-test/tests nem estão nos testpaths, e a segunda só passa com PYTHONPATH.
  • Uma função chamada testbench em test_agente.py é coletada como teste e devolve str (aviso do pytest).
Correção: skipUnless por ferramenta (ghdl, binutils, GPU) em vez de falhar; versionar ou gerar a fixture do Quartus; um alvo único (make test) com dependências declaradas.

M3 · CI morto médiaexecutado

.github/workflows/toolchain-smoketest.yml dispara por mudanças em legado/toolchain_smoketest/** e roda make -C /var/www/legado/toolchain_smoketest/test/. A pasta legado/ não existe. Nenhum workflow roda pytest.

Correção: apagar ou apontar o workflow; adicionar um job que rode rvverify/tests e rvgen/tests (os que não precisam de simulador).

M4 · agente.py é um monólito médiamedido

5.457 linhas, 147 funções. _testar_componentes tem 720 linhas, _corrigir 352, e há 6 funções com mais de 100. É o arquivo que mais vai mudar e o mais difícil de revisar ou testar por partes (o test_agente.py já tem 1.252 linhas).

Sugestão: separar por fase em módulos (arquitetura, contratos, componentes, triagem, correcao_cpu) mantendo Agente como fachada. Fazer depois de A1–A5, com os testes atuais como rede.

M5 · Cliente de LLM sem retry e sem schema médialido

post_json converte qualquer erro HTTP/timeout em ErroLLM e para. Não há retry nem backoff para 429/5xx, e o ClienteOpenAI descarta o schema (del schema). Em rodadas longas e pagas, um soluço de rede derruba a sessão; retomar só existe com as flags de portão.

Sugestão: 3 tentativas com backoff exponencial para 429/5xx/timeout; usar response_format do OpenRouter quando o modelo suportar.

M6 · Sem teto de custo médiamedido

O prompt de sistema tem ~13 KB e vai em toda chamada. O único limitador é --iteracoes (12), que não conta as chamadas de contrato, triagem, testbench e diagnóstico. O custo só aparece depois, em comparar, como estimativa.

Sugestão: --max-chamadas e --max-tokens com parada limpa; mostrar o acumulado a cada fase; fazer a primeira rodada pequena (RV32I, monociclo, poucas iterações) para medir.

M7 · Dependências não declaradas médialido

O pyproject.toml da raiz só configura o pytest. Nada declara cocotb>=2 (o rvverify.builder importa cocotb_tools). O .venv local tem Streamlit e Altair da trilha A e não tem cocotb. O README diz “só biblioteca padrão” para o rvgen, mas o component_runner precisa de cocotb.

Sugestão: [project] com extras (rvgen, sim, dev) ou um requirements.txt por ambiente, e um passo único “preparar o WSL”.

M8 · VHDL e teste pelo mesmo modelo médialido

Já discutido: a separação é só de contexto; os pontos cegos do modelo são os mesmos nos dois lados. O juiz oficial é o contrapeso.

Sugestão: permitir um segundo modelo só para testbench e triagem (configuração por papel).

B · Menores baixa

  • .gitignore cita specs/tasks.md (T0.4) e “ADR-018”, que não existem mais; docker/README.md e o Dockerfile citam NFR-RV-05, ADR-004 e ADR-005.
  • O mapa de memória (RAM_BASE 0x00FC8100, 512 bytes) está repetido em tb_virtual.py, conformance.py e contrato.py e não aparece em specs/cpu.md.
  • O rvverify exige Python 3.11+ (tomllib); o README diz “Linux/WSL2” mas o pyproject não fixa versão.
  • Digests de imagem Docker datados (28/09/2026) no README ficam velhos a cada push.
  • O examples/ local e outputs/ sobraram da trilha A; apagar.

7 · O que está bem feito

Segurança do juiz

A IA só escreve em src/*.vhd (_destino recusa o resto), e os arquivos do validador são conferidos por hash antes e depois da geração; se mudaram, o veredito é recusado.

Disciplina de correção

Uma correção por vez, medida de novo, e desfeita se piorar; regressões viram testes; resposta repetida sobe a temperatura.

Honestidade das métricas

Veredito só de execução; rvverify tem teste para “não aprovar em vazio”; métricas ausentes saem como “não observável”; custo rotulado como estimativa.

Auditoria

Cada chamada à LLM grava prompt, resposta, tokens e tempo. retomar continua a partir dos blocos congelados por hash.

Testes do agente

139 testes passam usando um servidor falso, sem gastar token nem precisar de simulador.

Quartus

Relatório com números reais do Quartus (Fmax, ALMs, potência), com fixtures de log para testar o parser.

8 · Limites desta revisão

  • Não rodei simulação nenhuma (sem GHDL, cocotb nem compilador RISC-V neste PC). Achados A3 e M1 são por leitura; A1, A5, M2, M3 e os números de testes foram executados.
  • Não chamei a LLM nem medi custo ou tempo.
  • Não reli os ~9.000 linhas de cpus/ nem o quartus_cpu_check.py por dentro; descrevo o papel deles pelos READMEs e docstrings.
  • Do agente.py li o fluxo principal, a triagem, a correção e os prompts centrais, não as 5.457 linhas.
